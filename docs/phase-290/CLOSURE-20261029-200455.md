## Scope
Closes Phase 289 gaps:
- **G1** no CAS on sequence advance (concurrent same-sequence writers could both overwrite last_sequence)
- **G4** messageId accept not atomic with sequence advance (concurrent same-messageId requests both advanced sequences; only one insert took effect; both handlers ran)

## Design
Preflight (session read, freshness check, timestamp, JOB_RESULT integrity) unchanged from Phase 289. Then inside one SQLite transaction:

1. CAS on `worker_sessions.last_sequence` (`UPDATE ... WHERE last_sequence < ?`)
2. `INSERT OR IGNORE` into `worker_message_ids`

If either fails, the transaction ROLLS BACK. The handler never runs for a rejected request. **This is the essential fix vs the initial buggy version where runAccept returned silently on failure and better-sqlite3 committed anyway.**

On success, the transaction commits BEFORE the handler. Handler failure after commit does NOT undo acceptance (**Strict B1**): client retries with a new messageId + new sequence.

**Non-SQL engines** fall back to Phase 289 behavior (their transaction() throws SQL_UNSUPPORTED). Documented in gateway code.

## Known limitations
1. CAS applies only to SQLiteEngine (kind === 'sqlite'). Memory/IndexedDB fall back to Phase 289 behavior.
2. Cross-process safety NOT claimed (single-process production). SQLite file locks are correct but untested cross-process.
3. Strict B1: handler-failure-after-accept consumes the message. Retries use fresh identifiers.
4. JOB_CANCEL external cancel window: crash after accept but before cancelDetailed completes means cancel not issued. T16 verifies no DB tx spans the await.
